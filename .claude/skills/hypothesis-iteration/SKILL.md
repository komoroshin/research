# Итерация продуктовой гипотезы

Третья стадия каскада **idea-check → pitch-build → hypothesis-iteration**:
идея проверяется (скилл `idea-check`, результат — паспорт гипотезы),
из паспорта собираются питч-артефакты (скилл `pitch-build`), и этот скилл
ведёт их итерации по фидбеку. Паспорт/профиль проекта — общая эстафетная
палочка всех трёх стадий: читай его первым, дополняй по ходу.

Этот скилл закрепляет цикл работы над продуктовой гипотезой и её
питч-артефактами (дека, одностраничник, письмо, финмодель), когда приходит
фидбек стейкхолдера — инвестора, комитета, ментора — или появляется новая
гипотеза, требующая проверки фактами.

Цель каждой итерации формулируется просто: после неё на каждый заданный
вопрос существует прямой ответ в артефакте, каждое число имеет источник,
а каждое допущение названо допущением. Инвестор, задавший вопрос, должен
увидеть ответ там, куда посмотрит, — не в переписке, а на слайде.

## Обзор цикла

1. **Разбор фидбека** → список явных вопросов и план изменений
2. **Параллельное исследование** → по одному субагенту на вопрос
3. **Правки артефактов** → дисциплина источников и фиксация решений
4. **Проверки** → автоматические проверки и вёрстка
5. **Зеркальные артефакты** → письмо-ответ, финмодель, выгрузки

Перед стартом проверь `references/` этого скилла: если для проекта есть
профиль (например, `references/threshold.md`), он определяет конкретные
файлы, тесты и процесс публикации — читай его первым. Если профиля нет,
работай по общим правилам ниже и в конце итерации предложи пользователю
создать профиль: вторая итерация с профилем идёт заметно быстрее первой.

## 1. Разбор фидбека

Фидбек почти никогда не приходит списком чётких вопросов — это абзац
пожеланий, реплика с встречи, «хотелось бы, чтобы смотрелось интереснее».
Первый шаг — превратить его в таблицу:

| Вопрос стейкхолдера | Что меняется и где | Чем подтверждаем |
|---|---|---|
| «масштаб проблемы» | слайд 2: добавить стоимость проблемы в $/год | исследование: источники по прямым и непрямым издержкам |
| «в чём уникальность» | слайд с конкурентами: вынести рамкой | решение по подаче, исследование не нужно |

Третья колонка сразу делит вопросы на три типа: нужно **исследование**
(агент), нужен **расчёт** (арифметика из уже одобренных чисел), нужно
**решение автора** (позиционирование, что показывать, что снять). Не
отправляй агентов исследовать то, что решается подачей.

Отдельно помечай вопросы, на которые артефакт формально «уже отвечает»:
если вопрос всё равно задали — ответ не считывается. Это задача на подачу
(вынести отдельной рамкой, переформулировать, переставить), а не на новый
контент.

Покажи таблицу пользователю до начала работ — это дешёвая точка сверки,
которая экономит целую итерацию, если какой-то вопрос понят не так.

## 2. Исследовательские агенты

Запускай по одному субагенту на исследовательский вопрос — **всех в одном
ходу, параллельно, в фоне** (Agent tool, тип general-purpose). Типовые
направления: размер рынка и TAM/SAM/SOM, стоимость проблемы для экономики,
сделки-аналоги и мультипликаторы, конкурентная карта, регуляторные рамки.

Шаблон брифа агенту:

```
Исследуй: <конкретный вопрос>.
Контекст продукта: <2–3 предложения — что за продукт, рынок, стадия>.
Нужен результат в виде: <таблица сделок / оценка с диапазоном / список
источников по тезису>.
Дисциплина источников (обязательно):
- каждое число сопровождай источником (название, год, ссылка);
- предпочитай первичные источники (CDC, рецензируемые журналы, отчёты
  компаний, пресс-релизы сделок) агрегаторам и блогам;
- если точного числа нет — давай диапазон и называй метод оценки;
- всё, что не факт, а допущение, помечай словом «допущение»;
- не смешивай пересекающиеся категории без оговорки о пересечении.
Сохрани результат в <файл>.
```

Почему по одному вопросу на агента: узкий бриф даёт проверяемый результат
и параллелится; агент с брифом «исследуй всё» возвращает обзор, из
которого нельзя взять число на слайд. Если инструмент запуска субагентов
в среде недоступен — проведи те же исследования сам, последовательно, по
тем же брифам и с той же дисциплиной источников.

Правила работы с результатами исследования:

- **TAM/SAM/SOM** — считай по стандартным допущениям: TAM — все, у кого
  есть проблема; SAM — досягаемый сегмент, готовый платить выбранным
  способом; SOM — не «доля рынка», а арифметика из уже одобренного
  бюджета (бюджет теста ÷ ожидаемый CAC = измеримое число покупателей).
  Если категории TAM пересекаются — оговорка об этом ставится на слайд,
  не в заметки.
- **Сделки-аналоги** — для каждой: покупатель, актив, год, параметры
  (сумма или мультипликатор), источник. Отдельной строкой — что именно
  покупали (данные, аудиторию, протокол, команду): это и есть аргумент
  «почему купят нас».
- **Стоимость проблемы** — раскладывай на прямые и непрямые издержки и
  давай итог с диапазоном; одно круглое число без раскладки не переживёт
  первый же вопрос.

## 3. Правки артефактов

- **Каждое число трассируемо.** У числа на слайде есть источник в сноске,
  заметках или приложении. Число без источника — это будущий вопрос
  инвестора, на который никто не сможет ответить.
- **Допущения — на слайде.** Если SOM построен на допущении о CAC, слово
  «допущение» стоит рядом с числом. Явное допущение выглядит честно;
  вскрытое инвестором — как попытка обмануть.
- **Решения автора фиксируются письменно.** Снятая формулировка, причина
  отказа от обещания, позиция по спорному вопросу — записывай в заметки
  спикера или README проекта. Через месяц никто не вспомнит, почему
  фраза была снята, и она вернётся.
- **Не переписывай историю.** Исторические разделы документации не
  перенумеровывай под новую структуру — помечай, к какой версии они
  относятся.
- **Считай зависимые места.** Вставка слайда тянет перенумерацию ссылок в
  тестах, документации и прозе. Ищи ссылки и по числу, и по словоформам
  («слайд 12» и «Слайд 12» — регистрозависимый поиск пропустит одно из
  двух).

## 4. Проверки

Если у проекта есть профиль — гоняй его набор проверок после каждой правки,
целиком, а не выборочно. Если профиля нет, минимальный набор, который
стоит собрать даже в виде одноразового скрипта:

- **сверка чисел**: числа в артефакте совпадают с числами исследования;
- **запрещённые формулировки**: снятые обещания и опасные фразы не
  вернулись (регулярки по списку);
- **утечка внутреннего**: заметки и внутренние разделы не попадают в
  публичную копию (проверка маркерной фразой);
- **вёрстка**: для визуальных артефактов — проверка переполнения текста
  на реальном рендере, а не на глаз.

Проверки — это не бюрократия: цикл повторяется много раз, и каждая
регрессия, пойманная скриптом, — это вопрос, который инвестор не задаст.

## 5. Зеркальные артефакты

Ответ стейкхолдеру — не только правки деки. Собери:

- **Письмо-зеркало**: та же нумерация и формулировки вопросов, что у
  стейкхолдера, по каждому — короткий ответ и номер слайда. Стейкхолдер
  проверяет ответы по своему списку — облегчи ему проверку.
- **Финмодель-отправная точка**: константы берутся из артефактов (цены,
  бюджеты, CAC), рычаги помечены как допущения, результат — 2–3 сценария.
  Не строй подробную модель на куче неизвестных — стройная простая модель
  с честными допущениями убедительнее фальшиво-точной.
- **Выгрузки для смежных инструментов** (текст для дизайнера, экспорт в
  другой формат) генерируй скриптом из единого источника, а не руками:
  ручная копия отстанет после второй же правки.

## Профили проектов

Профиль проекта — конкретика: пути к файлам, формат контента, набор
тестов, процесс публикации, постоянные ограничения и список зеркальных
артефактов. Искать его в двух местах: паспорт гипотезы в репозитории
проекта (его создаёт стадия `idea-check` и дополняет `pitch-build`) и
`references/` этого скилла.

- `references/threshold.md` — рабочий пример (дека Threshold,
  komoroshin/research).

Когда итерация завершена в проекте без профиля, предложи пользователю
записать профиль по образцу threshold.md — в него идёт всё, что пришлось
выяснять по ходу: где лежит контент, как проверять, как публиковать, что
нельзя.
