# Работа с research

## Начало задачи

- Общайся с владельцем по-русски. Прочитай корневой README.md и документацию нужного подпроекта.
- Это несколько независимых сайтов и приложений. Определи нужную папку до правок; не переноси изменения во все проекты автоматически.
- Проверь текущую ветку и `git status`. Сохраняй чужие незакоммиченные изменения.
- Не считай историю чата Claude доступной: восстанавливай контекст по файлам, истории Git и задаче пользователя.

## Карта исходников

- Корневой `index.html` и папки `debitorka/`, `animaccord/`, `aureum-quote/`, `app/`, `brand/`, `deck/`, `prototype/`, `smoke/` содержат статические материалы. Их HTML/CSS/JS редактируются непосредственно.
- `ai-case-library/src/` — внутренняя библиотека; её сборка публикуется в `cases/`.
- `ai-case-library/client-app/` — клиентский каталог; сборка в `catalog/`.
- `ai-case-library/scale-app/` — проекты клиентского масштаба; сборка в `projects/`.
- `ai-case-library/solutions-app/` — каталог предложений; сборка в `solutions/`.
- `cases/`, `catalog/`, `projects/`, `solutions/` — результаты сборки. Исправляй исходники, затем пересобирай нужное приложение; не правь минифицированные файлы вручную.
- `games/homm3/` — игра с README, документацией, тестами и инструментами. Не путай с отдельными `games/heroes/` и `games/heroes3/`.

## Команды и проверки

Для React-приложений рабочая папка — `ai-case-library/`. Зависимости: `npm ci` по существующему lock-файлу. Не обновляй зависимости попутно.

| Изменённая часть | Сборка | Браузерный чек-лист |
|---|---|---|
| Внутренняя библиотека | `npm run build` | `npm run test-ui` |
| Клиентский каталог | `npm run build-client` | `npm run test-client-ui` |
| Проекты масштаба | `npm run build-scale` | `npm run test-scale-ui` |
| Предложения | `npm run build-solutions` | `npm run test-solutions-ui` |

- При изменении общей базы или общих модулей проверяй все затронутые приложения.
- После изменения основной базы запускай `npm run validate-data`. Эта команда обновляет `research/validation-report.txt`; отделяй реальное изменение отчёта от обновления времени проверки.
- Браузерные чек-листы требуют Playwright, браузер и запущенные preview-серверы. В текущих файлах указан Linux-путь `/opt/pw-browsers/chromium`, а Playwright отсутствует в package.json. Не объявляй UI проверенным только по успешной сборке; сначала настрой среду или сообщи ограничение.
- Тесты правил игры из корня: `node games/homm3/test/run.js`. При визуальных изменениях дополнительно проверяй соответствующий экран, включая мобильную ширину.
- Для статических страниц используй локальный HTTP-сервер и проверяй изменённую страницу в браузере. Не считай компиляцию других приложений проверкой лендинга.

## Исследовательские данные

- Основная база: `ai-case-library/data/cases.json`; допустимые классификаторы: `data/taxonomy.json`. Методология — в README библиотеки и `research/RESEARCH-BRIEF.md`.
- `data/small-cases.json` — база проектов масштаба; `data/offers.json` — предложения.
- Не придумывай клиентов, метрики, бюджеты, сроки или источники. Разделяй факты, заявления поставщика, прогнозы и интерпретации.
- Не редактируй вручную производные CSV и `*/src/generated/`: используй соответствующие скрипты.
- `merge-research` и `pipeline` пересобирают данные из сырья, а не просто проверяют их. Не запускай их как универсальный тест: прямые правки базы могут быть перезаписаны.
- Сохраняй белые списки полей в генераторах клиентских данных и обезличивание scale-каталога. Отсутствие поля в клиентском бандле не делает исходный публичный Git-репозиторий закрытым.

## Дизайн и существующие навыки

- Сохраняй стиль конкретного подпроекта, адаптивность и существующие шрифты.
- В `.claude/skills/` сохранены инструкции по интерфейсам, доступности, типографике, цветам и текстам. При соответствующей задаче прочитай нужный `SKILL.md` и его необходимые ссылки как материалы проекта. Наличие этой папки само по себе не означает автоматическую установку навыков в Codex.
- Не удаляй материалы Claude при адаптации для Codex.

## Публикация и отчёт

- `deploy-pages`, `deploy-catalog`, `deploy-projects`, `deploy-solutions` заменяют соответствующие локальные каталоги опубликованной сборки. Сами эти команды не выполняют git push.
- Пересборку опубликованных файлов выполняй при задаче обновить соответствующий сайт. Учитывай, что push в публикуемую ветку может обновить GitHub Pages.
- В результате перечисли изменения, реально выполненные проверки, известные ограничения и статус публикации. Не выдавай локальные изменения за сохранённые на GitHub.
