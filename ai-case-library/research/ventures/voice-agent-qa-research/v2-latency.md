# V2 — Латентность агентного голосового диалога с вызовом инструментов

Дата: 2026-09-01. Все числа — с источниками. Пометка «допущение» стоит там, где вывод мой, а не измерение.

Проверяемое утверждение: «Агентный голосовой диалог с вызовом инструментов (запись в систему,
поиск по истории объекта) достижим на локальном узле с задержкой, при которой разговор не разваливается».
Порог опровержения: если отраслевой предел 4–10 с при вызове инструментов не преодолевается
на локальном железе — гипотеза закрыта.

---

## ВЕРДИКТ: достижимо при условии X — **гипотеза НЕ закрывается**

Порог опровержения не сработал. Отраслевые 4–10 с из Full-Duplex-Bench-v3 — это **не физический
предел, а свойство конкретной связки** «облачная фронтир-модель + классический VAD-эндпойнтинг +
последовательный конвейер + сетевой round-trip до SaaS-инструмента». Каждая из четырёх составляющих
уже опровергнута отдельным измерением:

| Что «доказывает» 4–10 с | Контр-измерение | Источник |
|---|---|---|
| Каскад = 10.12 с | Стриминговый каскад с function calling = **755 мс** до первого звука | Salesforce, arXiv:2603.05413 |
| Лучший в мире = 4.25 с | Full-duplex с параллельным каналом действий = **0.64 с** до вызова инструмента, 0.27–0.40 с turn-taking | DuplexSLA, arXiv:2605.20755 |
| Решение о вызове инструмента дорогое | 0.5B-модель на RTX 4090: **51 мс P50** на генерацию вызова | SimpleTool, arXiv:2603.00030 |
| Локально медленнее облака | TinyAgent-1.1B на MacBook M3, 16 функций: **2.9 с** и 80.06% против GPT-4-Turbo **3.9 с** и 79.08% | arXiv:2409.00608 |

**Условие X (все пункты обязательны, ни один сам по себе не спасает):**
1. **Семантическая детекция конца реплики** вместо порога тишины — здесь лежит бóльшая часть 4–10 секунд.
2. **Стриминговый конвейер или нативный дуплекс с параллельным каналом действий** — вызов инструмента
   не должен останавливать речь и слушание.
3. **Маленькая дообученная модель на фиксированном наборе ~10 инструментов** + prefix-кэш схем инструментов.
4. **Спекулятивное исполнение только для read-only** («поиск по истории объекта»), запись — строго
   после подтверждения. Это совпадает с требованием безопасности, а не противоречит ему.
5. **Филлер/бэкчаннел** на хвост задержки.
6. **Локальные данные** — вызов инструмента стоит миллисекунды вместо 0.4–1.2 с сетевого round-trip.

**Настоящий риск гипотезы — не миллисекунды, а точность.** См. раздел «Что реально может убить продукт».

## 1. Разложение задержки: из чего складываются 4–10 секунд

### 1.1 Как меряет сам бенчмарк
Full-Duplex-Bench-v3 (arXiv:2604.04847, 15.04.2026) режет задержку на три точки:
**First Word** (любая речь, включая филлер) → **Tool Call** (первый вызов API) →
**Task Completion** (фактический ответ). Table 6, секунды:

| Модель | First Word | Tool Call | Task Completion |
|---|---|---|---|
| GPT-Realtime | 6.36 | 3.89 | 6.89 |
| Gemini Live 2.5 | 7.03 | 4.61 | 7.26 |
| Gemini Live 3.1 | 3.95 | 2.21 | **4.25** |
| Grok | 5.97 | **0.63** | 6.65 |
| Ultravox v0.7 | 3.88 | 6.01 | 8.40 |
| Cascaded (Whisper→GPT-4o→TTS) | 8.78 | 3.15 | **10.12** |

**Первая же аномалия ломает интерпретацию «4–10 с = стоимость вычислений»:** у Grok вызов
инструмента происходит через **0.63 с**, а фактический ответ — через 6.65 с. Между этими
двумя точками почти нет вычислений. Значит основная часть — это **политика ожидания и
детекция конца реплики**, а не инференс.

### 1.2 Покомпонентная раскладка (сведено из источников)

| Компонент | Что стоит в облачном/бенчмарочном сетапе | Что стоит на локальном узле | Источник |
|---|---|---|---|
| Детекция конца реплики | 500–800 мс порога тишины, причём Silero VAD попадает в границу ±320 мс лишь в **33.9%** (порог 320 мс) и **10.4%** (порог 480 мс) — то есть систематически решает поздно | Семантический детектор: **23–152 мс** инференса, попадание в границу **86.7%**, раннее перебивание 5.0% | Next-Turn, arXiv:2606.18094 |
| ASR | Whisper батчем — главный вклад в 8.78 с first word у каскада | streaming: **15–50 мс/чанк**; Parakeet.cpp ~27 мс энкодер на 10 с аудио | FDB-v3; modelslab 2026 |
| Решение о вызове (LLM) | облачный TTFT **180–600 мс** + сеть; на длинных схемах инструментов префилл растёт | **51 мс P50** (Qwen2.5-0.5B, RTX 4090, parallel decoding); локальный TTFT в целом 15–80 мс | SimpleTool, arXiv:2603.00030; sitepoint 2026 (блог) |
| Исполнение вызова | внешняя CRM: **410 мс p50 / 1240 мс p95**; векторный поиск в облаке 50–300 мс | локальная БД: единицы мс; предиктивный кэш **0.35 мс** (316× при 75% попаданий) | speechify.ai; VoiceAgentRAG, arXiv:2603.02206 |
| Генерация ответа после результата | второй облачный round-trip: ещё 180–600 мс + префилл | второй локальный TTFT: 15–80 мс | те же |
| Синтез речи (TTFB) | облачный TTS + сеть | Kokoro локально: **28–100 мс**; Orpheus ~200 мс | inworld.ai 2026 |
| **Сумма до первого звука** | **1.5–3 с даже без ошибок эндпойнтинга** | **~350–700 мс** | сложение выше (допущение) |

### 1.3 Четыре источника «лишних» секунд, которых на локальном узле нет или они устранимы

1. **Эндпойнтинг на спонтанной дизфлюентной речи — главный.** FDB-v3 специально построен на
   реальной речи с «э-э», паузами и самокоррекцией (21 сценарий с откатом состояния).
   Классический VAD на такой речи почти всегда срабатывает поздно. Это объясняет разрыв
   First Word 3.9–8.8 с при Tool Call 0.63 с у Grok.
2. **Двойной сетевой round-trip.** Ход с инструментом требует минимум двух обращений к модели
   (решить → ответить). При 180–600 мс на обращение это 0.4–1.2 с чистой сети, которых на
   локальном узле нет вообще.
3. **Round-trip до внешней системы.** 410 мс p50 / 1240 мс p95 на чтение контакта в облачной CRM.
   Запись в локальную систему — миллисекунды.
4. **Последовательность конвейера.** Авторы FDB-v3 прямо пишут: у каскада «последовательная
   цепочка Whisper→LLM→TTS создаёт неустранимое узкое место» (first word 8.78 с). Стриминговая
   версия того же каскада даёт 755 мс (Salesforce). Это разница архитектуры, а не железа.

## 2. Обходные приёмы и их цена в миллисекундах

| Приём | Выигрыш | Цена / риск | Источник |
|---|---|---|---|
| **Параллельный канал действий** (вызов инструмента идёт синхронно с речью, на такте 160 мс) | Tool-call delay **0.64 с** против 2.77 с у каскада (~4×); turn-taking **0.27–0.40 с** против 0.68–1.68 с у GPT-Realtime | Точность вызова 85.6% в среднем (75.0% на мультидействии) | DuplexSLA, arXiv:2605.20755 |
| **Спекулятивный вызов + асинхронный I/O** (старт вызова до конца реплики; safe/unsafe разделение) | Облако: 7.6 → 4.4 с (1.7×). **Локальные дообученные 3B: 4.1 → 2.5 с и 2.7 → 1.2 с (1.6–2.2×)** | Точность −0.6…−1.7 п.п.; **на натуральной речи проседает до 13.6–22%** | Speculative Interaction Agents, arXiv:2605.13360 |
| **Предиктивный кэш извлечения** («медленный мыслитель» греет кэш в фоне) | Извлечение **110.4 мс → 0.35 мс**, hit rate 75% (79% с 2-го хода) | Промахи возвращают полную стоимость | VoiceAgentRAG, arXiv:2603.02206 |
| **Prefix-кэш KV для системного промпта и схем инструментов** | TTFT **−60…−80%**; замер: 4.3 с → 0.6 с на промпте ~10 000 токенов | Работает только при неизменном префиксе → аргумент за фиксированный набор инструментов | vLLM docs; llm-d.ai |
| **Параллельное декодирование вызова + сжатие токенов** | 110.1 → **51.0 мс** (0.5B, 4.3×); 468.5 → ~61.2 мс (4B, 7.7×) | Точность растёт (+7.1 п.п.), не падает | SimpleTool, arXiv:2603.00030 |
| **Семантическая детекция конца реплики** | Попадание в границу 33.9% → **86.7%**; ранние перебивания 31.1% → 5.0% | Сам детектор стоит 23–152 мс | Next-Turn, arXiv:2606.18094 |
| **Филлер-речь** | Не сокращает задержку, но переводит паузу 2–4 с из «сломалось» в «работает»: уместность 5.83 против 4.04 по 7-балльной шкале, 66.7% предпочитают | Без хорошего эндпойнтинга даёт перебивания: у Ultravox **47.9%** реплик накладываются на речь пользователя | arXiv:2508.11781 (N=24); FDB-v3 |
| **Сокращение числа инструментов** | Время исполнения **до −70%**, энергия до −40%, успешность растёт | Требует, чтобы домен реально был узким | Less-is-More, DATE 2025, arXiv:2411.15399 |

**Важно про спекуляцию и запись в систему.** Speculative Interaction Agents делят инструменты на
**safe (read-only)** и **unsafe (запись)**: unsafe придерживаются до финального подтверждения.
Это ровно наш случай: «поиск по истории объекта» можно спекулятивно запускать с середины реплики,
«запись в систему» — нельзя. То есть приём даёт выигрыш именно там, где он безопасен, и не
конфликтует с требованием человека в цикле.

## 3. Узкий домен: снижается ли задержка радикально

Да, но не сам по себе — только в связке с маленькой моделью и правильным конвейером.

- **Less-is-More (DATE 2025, arXiv:2411.15399)**: избирательное сокращение числа доступных
  инструментов на краевых устройствах даёт **до −70% времени исполнения и до −40% энергии**,
  при этом успешность агентных задач растёт. Метод без дообучения.
- **TinyAgent (arXiv:2409.00608, UC Berkeley)** — прямой аналог кейса: **16 фиксированных функций**,
  голосовой ввод, всё локально на MacBook Pro M3. TinyAgent-1.1B (4 бита, 0.68 ГБ): успешность
  **80.06%**, end-to-end **2.9 с**. GPT-4-Turbo из облака: 79.08% и 3.9 с. Локальная малая модель
  на узком наборе **и точнее, и быстрее фронтирной облачной**.
- **Speculative Interaction Agents**: дообученные Qwen2.5-3B и Llama-3.2-3B на TinyAgent-задачах —
  **2.5 с** после оптимизации против 4.4 с у облачного OpenAI Realtime на тех же задачах.
- **SimpleTool**: дообученный ST-Qwen-0.5B против FunctionGemma-270M на Mobile Actions —
  86.2% против 85.0% точности, **P50 51.0 мс против 61.1 мс, P90 74.5 мс против 139.5 мс**.
- **Prefix-кэш**: фиксированный набор из десятка схем инструментов не меняется от хода к ходу,
  значит его префилл кэшируется целиком (−60…−80% TTFT).

**Отрезвляющая оговорка.** FDB-v3 сам тестировал уже узкие домены — 2–3 функции на домен,
11 функций всего. И всё равно получил 4–10 с. **Узость набора без остальных условий задержку
не спасает** (допущение: причина в том, что у коммерческих API нельзя поменять ни эндпойнтинг,
ни архитектуру конвейера, ни сетевой путь — узкий набор экономит только префилл).

## 4. Локальное железо против облака при вызове инструментов

**Преимущество не только сохраняется — при вызове инструментов оно РАСТЁТ.** Причина в том,
что ход с инструментом умножает число сетевых обращений.

- Заявленные 15–80 мс локального TTFT против 180–600 мс облачного подтверждаются
  (RTX 5090 + 34B Q5: 20–45 мс; M4 Ultra: 25–55 мс) — но источник блоговый
  (sitepoint.com, 2026), помечаю как вторичный. Физика при этом на стороне утверждения:
  в облачных 180–600 мс доминирует сетевой round-trip, который моделью не оптимизируется.
- **Ход без инструмента**: 1 обращение к модели. Разница локально/облако ≈ 165–520 мс.
- **Ход с инструментом**: минимум 2 обращения к модели + 1 обращение к системе-инструменту.
  Локально: 2×(15–80 мс) + единицы мс на локальную БД ≈ **35–170 мс**.
  Облачно: 2×(180–600 мс) + 410 мс p50 / 1240 мс p95 на внешнюю CRM ≈ **770 мс – 2.4 с**.
  **Разрыв вырастает примерно с 0.2–0.5 с до 0.7–2.3 с на ход.** (Допущение: сложение
  независимых замеров из разных источников, не одно сквозное измерение.)
- Подтверждающие сквозные замеры локальных стеков:
  - Salesforce: стриминговый каскад с полной поддержкой function calling — **755 мс** TTFA
    (лучший случай 729 мс);
  - локальный Parakeet + Qwen3-8B + Kokoro: **984 мс** end-to-end при одном звонке
    (вторичный источник, замер на 100 конкурентных звонках);
  - TinyAgent-1.1B на M3: **2.9 с** полного цикла с голосом и вызовом функции.
- **Ограничение локального:** авторы Salesforce отдельно фиксируют, что полностью self-hosted
  end-to-end speech-to-speech пока не тянет (Qwen3-Omni локально на HF Transformers — ~146 с,
  нереально); практичная self-hosted архитектура сегодня — **стриминговый каскад**, а не
  нативный дуплекс. DuplexSLA хардварных требований не публикует.

## 5. Порог терпимости человека — и почему он переворачивает вывод

### 5.1 Что установлено для разговора
- Живая речь: люди системно избегают наложений и минимизируют паузы, типичный межрепликовый
  разрыв — сотни миллисекунд, универсально по 10 языкам
  (Stivers et al., PNAS 2009, 106(26):10587–10592, https://www.pnas.org/doi/10.1073/pnas.0903616106).
- Робот/агент: предпочтение по времени отклика максимально на **1 с**, оценки **выходят на
  плато к 2 с**; разговорный филлер существенно смягчает впечатление от длинного отклика
  (Shiwa, Kanda, Ishiguro, Hagita — HRI 2008 / Int. J. Social Robotics 2009,
  https://link.springer.com/article/10.1007/s12369-009-0012-8).
- Голосовые интерфейсы вообще: **< 2 с приемлемо; ~4 с — UX существенно падает; ≥ 8 с — стабильно
  очень низкие оценки** (порог, на который опираются Ma et al., CHI 2026,
  DOI 10.1145/3772318.3791747, https://arxiv.org/html/2603.19904v1).

### 5.2 Что установлено для рабочего сценария — а это другой режим
- **CHI 2026, «Quantifying Latencies»** (DOI 10.1145/3772318.3790947): в живых человек-агент
  диалогах медиана паузы агента — **4.1 с** против 1.2 с у человека, и при этом
  **пользователи далеко не всегда трактуют задержку как поломку**, требующую «ремонта» разговора.
  То есть 4 с не убивают взаимодействие автоматически — они убивают ощущение светской беседы.
- **Филлер сдвигает порог.** При задержках 2 / 4 / 8 с поведенческий филлер поднимает уместность
  с 4.04 до **5.83** и естественность с 3.75 до 4.71 по 7-балльной шкале; 66.7% предпочитают
  этот вариант (arXiv:2508.11781, N=24). Пауза с «сейчас посмотрю в карточке» — это уже не пауза,
  а работа.
- **Продакшн-планка для ровно нашего сценария.** Salesforce Field Service, голосовое заполнение
  формы техником в поле: целевое **сквозное время — менее 15 секунд**, при 85% точности заполнения
  полей; ASR на устройстве, один облачный round-trip на разбор в поля. Отдельная находка:
  **техники предпочитают прозрачность и возможность исправить, а не «тихую автоматизацию»**
  (https://engineering.salesforce.com/delivering-accurate-low-latency-voice-to-form-ai-in-real-world-field-conditions/).
- **FormBharo** (arXiv:2608.06027, 2026), голосовой агент для заполнения форм: заявленные целевые
  p95 — **< 55 с на извлечение и < 44 с на ответ**. Порядок величины показывает, насколько
  сдвинута планка в задачах заполнения формы против болтовни.

### 5.3 Ответ по пункту 5
**Да, пункт 5 переворачивает вывод — но не отменяет требования, а расслаивает его по типу хода.**
Единой «допустимой задержки» у диктовки отчёта нет; есть четыре разных бюджета (допущение —
это моя классификация, собранная из перечисленных источников, а не готовая шкала из статьи):

| Тип хода | Пример | Бюджет | Обоснование |
|---|---|---|---|
| Бэкчаннел / подтверждение приёма | «записал», «угу» | **< 1 с** | Плато предпочтения по Shiwa; DuplexSLA берёт 0.27–0.40 с |
| Зачитывание записанного / уточнение | «трещина 200 мм, верно?» | **1–2 с** | «< 2 с приемлемо» (порог, цитируемый CHI 2026) |
| Запрос к истории объекта | «что было на прошлом осмотре» | **2–3 с**, с филлером до 4 с | Плато к 2 с + филлер поднимает уместность 4.04 → 5.83 |
| Пакетная операция | «собери отчёт и отправь» | **секунды–десятки секунд** при видимом прогрессе | Salesforce: < 15 с как продакшн-цель для voice-to-form |

Практический вывод: **сокращать отраслевые 4–10 с надо не в 20 раз, а примерно вдвое** — и то
не везде. Сокращать «в 20 раз» (до 200 мс) нужно только для бэкчаннела и перебиваний, а это как
раз самая дешёвая часть: она не требует ни вызова инструмента, ни большой модели, и DuplexSLA уже
делает её за 0.27–0.40 с.

## Что реально может убить продукт (это не миллисекунды)

Дисциплина требует назвать: **связывающее ограничение — точность на спонтанной речи, а не задержка.**

1. **Потолок Pass@1.** Лучший в мире результат FDB-v3 — **0.600** (GPT-Realtime), на сложных
   сценариях — **0.433**. Для записи в систему осмотра это означает, что каждый второй-третий
   сложный ход требует исправления.
2. **Спекуляция ломается о натуральную речь.** Speculative Interaction Agents на датасете
   «Human Instructions» дают **13.6–22%** точности. То есть главный приём ускорения хуже всего
   работает именно на том материале, который у нас будет.
3. **ASR-ошибки съедают заполнение формы.** FormBharo: полнота заполнения формы падает
   **на величину до 41 п.п.** при переходе с эталонных транскриптов на реальные распознанные.
4. **Оптимизация задержки рождает свои отказы.** Gemini Live 3.1 — самая быстрая (4.25 с) — в
   **22%** случаев корректно вызывает инструмент и **молча не отвечает голосом**; Ultravox с
   филлерами перебивает пользователя в **47.9%** реплик.
5. **Нет ни одного опубликованного сквозного замера** полного локального узкодоменного
   голосового агента с вызовом инструментов на реальной дизфлюентной речи. Все приведённые
   числа — из разных сетапов, и их сложение это допущение, а не измерение.

### Что измерить, чтобы закрыть допущения (дёшево)
- Собрать локальный стенд «Parakeet-streaming + семантический эндпойнтер (LiveKit turn-detector
  или Next-Turn-tiny) + дообученная 0.5–3B на 10 функциях осмотра + Kokoro» и померить
  те же три метрики FDB-v3 (First Word / Tool Call / Task Completion) на **своих** записях
  реальных осмотров с дизфлюенциями. Ожидание по сложению источников: 0.5–1.5 с до фактического
  ответа. Это прямая проверка условия X.
- Померить Pass@1 на собственных 10 операциях — именно здесь гипотеза может умереть.

Что доминирует и что предлагают авторы:
- у каскада узкое место — first word 8.78 с, «последовательная цепочка Whisper→LLM→TTS создаёт
  неустранимое узкое место» (нет распараллеливания);
- **филлер-речь**: Ultravox почти всегда выдаёт «Let me check on that» до вызова API —
  снижает воспринимаемую задержку, но 47.9% реплик перекрывают речь пользователя (перебивает);
- **преэмптивный (спекулятивный) вызов инструмента**: доля преэмптивных вызовов —

  стартует рано, речь откладывается → Tool Call 0.63 с при First Word 5.97 с;
- обратная сторона оптимизации задержки: Gemini 3.1 — «молчаливый работник», 22% случаев
  инструмент вызван правильно, но ответа голосом нет.

**Ключевое наблюдение (моё, не из статьи — допущение к проверке):** метрики FDB-v3 отсчитываются
на спонтанной дизфлюентной речи. Разрыв First Word (3.9–8.8 с) и Tool Call у Grok (0.63 с)
показывает, что значительная часть «4–10 секунд» — это НЕ вычисление, а ожидание конца реплики
(эндпойнтинг на речи с паузами, «э-э», самокоррекцией) плюс политика когда начать говорить.

### Speculative Interaction Agents (arXiv:2605.13360v2)
Ссылка: https://arxiv.org/html/2605.13360v2
Механизмы: (а) асинхронный ввод-вывод — агент рассуждает, не блокируясь на ожидании
пользователя/среды; (б) спекулятивный вызов инструмента — вызов запускается до получения
полной реплики, потом правится или отменяется. Инструменты делятся на **safe (read-only)** и
**unsafe (запись)**; unsafe придерживаются до финального подтверждения. ← прямо релевантно
нашему кейсу: «поиск по истории объекта» = safe (спекулировать можно), «запись в систему» =
unsafe (нельзя, ждём подтверждения).

Измеренный выигрыш (end-to-end время до ответа):
- Cloud API (OpenAI Realtime): HotpotQA 4.5 с → 3.6 с (**1.3×**); TinyAgent 7.6 с → 4.4 с (**1.7×**)
- Qwen2.5-3B (дообучен): HotpotQA 2.7 с → **1.2 с** (2.2×); TinyAgent 4.1 с → **2.5 с** (1.6×)
- Llama-3.2-3B (дообучен): HotpotQA 2.3 с → **1.1 с** (2.1×); TinyAgent 5.0 с → **2.5 с** (2.0×)

Цена: HotpotQA 71.6% → 71.0%, TinyAgent 54.9% → 53.2% (потеря точности ~0.6–1.7 п.п.).
Hit-rate спекуляции и объём выброшенных вычислений авторы НЕ приводят.
Важная оговорка авторов: на датасете «Human Instructions» (натуральная речь) точность
падает до 13.6–22% — спекуляция плохо переносит спонтанную речь.

**Это самый важный численный результат для гипотезы:** маленькие (3B) дообученные модели
на узком наборе инструментов дают 1.1–2.5 с end-to-end — то есть уже ВНУТРИ отраслевого
порога, и в 2–4 раза быстрее облачного Realtime на тех же задачах.

### Порог терпимости человека — источники
- **Shiwa, Kanda, Ishiguro, Hagita. «How quickly should communication robots respond?»**
  HRI 2008 (ACM), расширено: Int. J. Social Robotics 1(2), 2009,
  https://link.springer.com/article/10.1007/s12369-009-0012-8
  Предпочтение по времени отклика системы (SRT) максимально на **1 с**, оценки
  **выходят на плато к 2 с** (дальше рост задержки уже мало меняет оценку).
  Ключевое: **разговорный филлер** («сейчас посмотрю») смягчает впечатление от длинного SRT —
  то есть 2 с с филлером воспринимаются как ~1 с без него.
- **Ma et al. «Beyond Words: Measuring User Experience through Speech Analysis in VUI»,
  CHI 2026**, DOI 10.1145/3772318.3791747, https://arxiv.org/html/2603.19904v1
  Тестировали задержки 0 / 4.5 / 9 с, UEQ+ (11 шкал). Цитируемый ими установленный порог:
  «**< 2 с — приемлемо; ~4 с — UX существенно падает; ≥ 8 с — стабильно очень низкие оценки**».
  Эффект ассистента доминирует над эффектом сценария (функциональный / творческий / игровой) —
  то есть по этим данным задержка бьёт одинаково во всех типах задач.
- «Voice-based UI for hands-free data entry at workplaces», MethodsX 2025,
  https://pmc.ncbi.nlm.nih.gov/articles/PMC12423416/ — **непригоден как источник по задержке**:
  батч-транскрипция файлов (3–6.5 мин на записи 223–600 с), пользовательского исследования нет.

### Salesforce AI Research, «Building Enterprise Realtime Voice Agents from Scratch» (arXiv:2603.05413)
https://arxiv.org/abs/2603.05413
- Их собранный каскад (streaming STT → vLLM-LLM → streaming TTS) **с полной поддержкой
  function calling**: **755 мс time-to-first-audio (лучший случай 729 мс)**.
- Qwen3-Omni через облачный API: ~702 мс audio-to-audio со стримингом;
  локально только Thinker: 516 мс; локально полный конвейер на HF Transformers: ~146 с (нереально).
- Вывод авторов: полностью self-hosted end-to-end speech-to-speech пока не тянет,
  **каскад со стримингом — практичная архитектура для self-hosted realtime**.
- ⚠️ Важно: их 755 мс — это TTFA (до первого звука), НЕ до фактического ответа после
  исполнения инструмента; и в стеке использованы облачные Deepgram/ElevenLabs. Требует уточнения.

**Противоречие, которое надо объяснить:** FDB-v3 даёт каскаду 10.12 с, Salesforce — 755 мс.
Разница не в железе, а в (а) метрике (Task Completion vs Time-to-First-Audio),
(б) речи (спонтанная дизфлюентная vs чистая), (в) стриминге (Whisper батчем vs streaming STT),
(г) сложности сценария (многошаговые цепочки API vs один вызов).

### TinyAgent: Function Calling at the Edge (arXiv:2409.00608, UC Berkeley/BAIR)
https://arxiv.org/html/2409.00608v1
Прямой аналог нашего кейса: **фиксированный узкий набор из 16 функций** (почта, контакты, SMS,
календарь, заметки, напоминания, файлы, Zoom), голосовой ввод, всё локально на **MacBook Pro M3**.
- TinyAgent-1.1B (4-бит, 0.68 ГБ): success rate **80.06%**, end-to-end **2.9 с**
- TinyAgent-7B (4-бит, 4.37 ГБ): **84.95%**, end-to-end 13.1 с
- GPT-4-Turbo (облако, референс): **79.08%**, **3.9 с**
Вывод: маленькая дообученная локальная модель на узком фиксированном наборе инструментов
**и точнее, и быстрее фронтирной облачной**. Покомпонентного разложения задержки авторы не дают.

### SimpleTool: Parallel Decoding for Real-Time LLM Function Calling (arXiv:2603.00030)
https://arxiv.org/html/2603.00030v1 — RTX 4090, vLLM, модели Qwen 0.5B…14B.
Латентность генерации самого вызова инструмента:
- Qwen2.5-0.5B: 110.1 мс → **51.0 мс** (4.3×); Qwen3-4B: 468.5 мс → ~61.2 мс с квантованием (7.7×)
- ST-Qwen-0.5B vs FunctionGemma-270M (Google, edge function calling, 12.2025) на Mobile Actions:
  P50 **51.0 мс** vs 61.1 мс; P90 **74.5 мс** vs 139.5 мс; точность после дообучения 86.2% vs 85.0%
- Точность не падает, а растёт: +7.1 п.п. в среднем по функциям.
**Следствие:** «решение какой инструмент вызвать и с какими аргументами» на локальном железе
стоит **десятки миллисекунд**, а не секунды. Это НЕ узкое место.

### Компонентные задержки локального стека (вторичные, отраслевые замеры 2026)
- ASR: faster-whisper / WhisperX 15–50 мс на чанк; Parakeet.cpp ~27 мс энкодер на 10 с аудио
  (Apple Silicon, 110M); Parakeet-Nemotron streaming — настраиваемая задержка 80–1120 мс.
  https://modelslab.com/blog/audio-generation/parakeet-cpp-vs-whisper-self-hosted-asr-comparison-2026
- TTS TTFB: Kokoro 50–100 мс, на локальной RTX 5090 — **28 мс** до первого аудио;
  Orpheus (Llama-3B + SNAC) ~200 мс. https://inworld.ai/resources/best-self-hosted-tts
- Полный локальный стек Parakeet + Qwen3-8B + Kokoro: **984 мс** end-to-end при 1 звонке
  (замер на 100 конкурентных звонках, Medium, вторичный источник — брать осторожно).
- LLM TTFT — обычно самое дорогое в связке: 150–300 мс.

### Эндпойнтинг — главный «немодельный» источник секунд (arXiv:2606.18094, Next-Turn, 2026)
https://arxiv.org/html/2606.18094v1 (Tsoi, Deng, Zhu et al.)
Задержка самого детектора на чанк: Silero VAD 3 мс; SmartTurn v2 29 мс; SmartTurn v3.2 21 мс;
EasyTurn 263 мс; Next-Turn (Whisper-tiny) 23 мс / small 52 мс / large 152 мс.
Точность попадания в границу реплики (ACC₃₂₀ — попал в ±320 мс от истинного конца):
- **Silero VAD с порогом 320 мс — 33.9%; с порогом 480 мс — 10.4%**
- SmartTurn v2 32.5%; v3.2 30.5%; EasyTurn 60.8%; **Next-Turn (Whisper-large) 86.7%**
- Ранние перебивания: Next-Turn-large 5.0% против EasyTurn 31.1%.
**Читается так:** классический VAD на спонтанной речи почти всегда решает ПОЗДНО — отсюда
секунды в First Word, а не из инференса. Семантический детектор конца реплики сам стоит
20–150 мс и попадает в границу в 87% случаев. Это и есть основной резерв сокращения.
LiveKit turn-detector: дообученный Qwen2.5-0.5B, ~0.1B параметров, CPU-инференс,
TPR >99.3% на 14 языках (https://huggingface.co/livekit/turn-detector).

### Ещё по порогу терпимости
- **«Quantifying Latencies: A Conversation Analysis Approach to Human-Agent Interactions in VR»,
  CHI 2026**, DOI 10.1145/3772318.3790947 — первое эмпирическое измерение пауз в живых
  человек-агент диалогах: медиана паузы у агента **4.1 с** против **1.2 с** у человека
  (в этой обстановке). Отдельно: **пользователи далеко не всегда трактуют задержку как поломку**,
  требующую «ремонта» разговора — часть задержки поглощается тем, что агент начинает говорить.
  Различают start-up latency (долго начинает) и wind-down latency (долго не замолкает при перебивании).
- Обзорное (вторичное): терпимость зависит не только от времени, но и от **сложности вопроса** —
  на сложный запрос пауза прощается. Первоисточник этой идеи — та же линия Shiwa/Kanda.

### Филлеры — сколько реально покупают
- **Shiwa et al. 2008/2009** (первично): филлер смягчает впечатление от длинного SRT; предпочтение
  максимально на 1 с, плато к 2 с.
- **«Behavioral and Symbolic Fillers as Delay Mitigation for ECAs in VR»**, IEEE TVCG / arXiv:2508.11781,
  2025, N=24, задержки **2 / 4 / 8 с**. Поведенческий филлер (анимация «думаю» + «хмм») против базы
  (7-балльная шкала): уместность 5.83 против 4.04; ожидаемость 5.79 против 4.33; естественность
  4.71 против 3.75 (p<0.001–0.002). 66.7% предпочли поведенческий филлер.
  Символические индикаторы (прогресс-бар) почти не помогли.
  → Филлер не убирает задержку, но **переводит 4-секундную паузу из «сломалось» в «работает»**.
- FDB-v3 показывает цену филлера без хорошего эндпойнтинга: Ultravox почти всегда говорит филлер
  и в **47.9%** реплик перебивает пользователя.

### Стоимость самого вызова инструмента (отраслевые замеры, вторичные)
- Векторный поиск в облачной БД (Qdrant/Pinecone/Weaviate): **50–300 мс** сетевого round-trip.
- Прод-лог Vapi → внутренний API → чтение контакта в HubSpot: **410 мс p50, 1240 мс p95**
  (https://speechify.ai/blog/voice-agent-tool-calls-inline-vs-handoff)
- Типовой разбор бюджета одного хода: вход 2.0 с, turn detection 0.3 с, обработка моделью 0.4 с,
  исполнение инструмента 0.7 с, генерация ответа 0.3 с → первый звук через 1.7 с.
  (https://www.c-sharpcorner.com/article/benchmarking-voice-agent-latency-from-speech-to-tool-execution/)
- Отраслевой ориентир: +300–400 мс уже «ломают ощущение живого звонка»; round-trip держат < 1.5 с.
**Для нас важно:** в облачном сценарии обращение к внешней CRM/БД стоит 0.4–1.2 с;
на локальном узле та же операция к локальной базе — единицы миллисекунд. Это чистый выигрыш
локального размещения, которого нет в тестах FDB-v3.

### Кэширование (обходной приём №4)
- **VoiceAgentRAG** (Salesforce AI Research, arXiv:2603.02206, 02.03.2026),
  https://arxiv.org/html/2603.02206v1 — двухагентная схема: «медленный мыслитель» в фоне
  предсказывает следующую тему и заранее тянет документы в FAISS-кэш в памяти;
  «быстрый говорун» сначала смотрит в кэш (<1 мс).
  Задержка извлечения **110.4 мс → 0.35 мс (316× на попаданиях)**; hit rate **75%** (150/200),
  на «тёплом» кэше с 2-го хода — 79%. Суммарно сэкономлено 16.5 с на 150 попаданиях.
- **Prefix caching / переиспользование KV-кэша**: для чатов с длинным общим системным промптом
  (2K+ токенов) TTFT падает на **60–80%**; замер на Qwen3-32B с промптом ~10 000 токенов:
  **4.3 с → 0.6 с (−78%)** при повторе. https://llm-d.ai/blog/kvcache-wins-you-can-see ,
  https://docs.vllm.ai/en/stable/design/prefix_caching/
  → В нашем кейсе описания 10 инструментов + системный промпт **неизменны от хода к ходу**,
  значит их префилл кэшируется полностью и стоит около нуля. Это прямой аргумент за узкий
  фиксированный набор инструментов.

### Локальное железо против облака (п.4)
- Замеры TTFT (вторичный источник, блог, помечаю как таковой):
  локальный инференс **15–80 мс** (RTX 5090 + CodeLlama-34B Q5_K_M: 20–45 мс; M4 Ultra: 25–55 мс),
  облачные API **180–600 мс**, где доминирует сетевой round-trip.
  https://www.sitepoint.com/local-vs-cloud-ai-coding-performance-analysis-2026/
  Другие источники дают 200–800 мс на облачный round-trip.
- Согласуется с физикой: сеть — это константа, которую нельзя оптимизировать моделью.

### Узкий домен как преимущество (п.3)
- **«Less-is-More: Optimizing Function Calling for LLM Execution on Edge Devices»**,
  DATE 2025, arXiv:2411.15399, https://arxiv.org/abs/2411.15399
  Ключевой результат: **избирательное сокращение числа доступных инструментов** улучшает
  качество function calling на краевых устройствах, при этом **время исполнения падает до −70%,
  энергопотребление до −40%**, а успешность агентных задач растёт. Метод без дообучения.
- TinyAgent (выше): 16 функций, 1.1B локально → точнее и быстрее GPT-4-Turbo.
- FDB-v3 сам по себе тестировал уже узкие домены (2–3 функции на домен) — значит
  «узость набора» одна, без правильной архитектуры, задержку не спасает. Нужна связка
  «узкий набор + маленькая дообученная модель + стриминговый конвейер + семантический эндпойнтинг».

### DuplexSLA — ключевое контр-измерение (arXiv:2605.20755, 20.05.2026)
https://arxiv.org/html/2605.20755v1
Нативно full-duplex модель со **синхронизированными каналами речи, текста и ДЕЙСТВИЯ**.
Такт разговора — **160 мс чанки**. Три канала: пользовательское аудио (2 причинных признака
на чанк по 80 мс), ассистент в раскладке TA4 (1 текстовый якорь + 4 аудио-токена с шагом 40 мс)
и **rate-limited текстовый канал действий** (до 10 текстовых токенов на чанк) — планирование
и структурные вызовы инструментов идут **не останавливая аудио ассистента**.
Бэкбон: инициализирован от Step-Audio 2 mini (в извлечении фигурирует «77B-scale» —
цифра выглядит подозрительно, **требует сверки по PDF**; на выводы о задержке не влияет).

Задержка вызова инструмента (их бенч DuplexSLA-Bench):

| Сценарий | DuplexSLA | Каскад ASR+LLM | Точность DuplexSLA |
|---|---|---|---|
| Одно действие | 0.67 с | 2.33 с | 85.67% |
| Мультидействие | 0.68 с | 4.71 с | 75.00% |
| Действие по бэкчаннелу | 0.57 с | 1.27 с | 96.00% |
| **Среднее** | **0.64 с** | **2.77 с** | **85.56%** |

Turn-taking (с префиллом контекста): normal 96.00% / 0.27 с; pause 93.33% / 0.27 с;
interrupt 99.33% / 0.40 с; backchannel 98.33% / 0.32 с.
Против GPT-Realtime High: 91.33% / 1.67 с; 90.33% / 1.68 с; 79.00% / 0.68 с; 0.33% / н/д.
Без префилла контекста против Gemini 3.1 Flash Live: 95.67% / **0.29 с** против 93.67% / 1.16 с.
Авторская формулировка: «DuplexSLA — единственная субсекундная система с конкурентной точностью;
коммерческие API достигают высокой точности, но платят >1 с задержки».

⚠️ Оговорки: (а) это собственный бенч авторов, речь там, вероятно, чище, чем в FDB-v3;
(б) точность мультидействия 75.00% — ниже, чем хотелось бы для записи в систему;
(в) требования к железу и real-time factor авторы не публикуют → **пригодность для локального
узла не доказана**, это открытый вопрос.
