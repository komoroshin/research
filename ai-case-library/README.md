# AI Case Library

Исследовательская и sales-библиотека **подтверждённых внедрений AI/ML/LLM в бизнесе**.
Статическое приложение без бэкенда: React + Vite + TypeScript, данные лежат рядом в JSON.

Библиотека отвечает не на вопрос «кто где использует AI», а на более полезный:

> Если перед нами компания такого типа — какие реальные AI-кейсы уже доказали ценность
> в похожих процессах и с какой гипотезой имеет смысл идти к клиенту?

Поэтому каждая запись существует одновременно как **research evidence** и как
**sales intelligence asset**.

## Быстрый старт

```bash
npm install
npm run dev          # локальный сервер разработки
npm run build        # production-сборка в dist/
npm run preview      # посмотреть собранное
```

Проверки данных:

```bash
npm run validate-data   # схема, таксономия, метрики без источников, дубли, квоты
npm run check-links     # доступность всех URL: working / redirect / unavailable / broken
npm run build-csv       # сгенерировать data/cases.csv из data/cases.json
npm run report          # пересобрать research/research-report.md
npm run summary         # пересобрать research/executive-summary.md
```

Пересборка базы из исходных материалов исследования:

```bash
npm run merge-research  # research/raw/*.json -> data/cases.json + сводные журналы
npm run repair-csv      # починить CSV с незакавыченными запятыми (входит в merge-research)
npm run pipeline        # merge + validate + csv + report + summary одной командой
```

Публикация:

```bash
npm run build           # сборка в dist/
npm run deploy-pages    # скопировать dist/ в <repo>/cases/ для GitHub Pages
```

## Структура репозитория

```
ai-case-library/
├── data/
│   ├── cases.json            # основная база (источник истины)
│   ├── cases.csv             # генерируется из cases.json, не редактировать руками
│   └── taxonomy.json         # нормализованные справочники всех классификаторов
├── research/
│   ├── RESEARCH-BRIEF.md     # регламент исследования для исполнителей
│   ├── raw/                  # выдача каждого направления исследования
│   ├── candidates.csv        # все рассмотренные кандидаты
│   ├── rejected.csv          # отклонённые с кодом причины
│   ├── source-log.csv        # каждый открытый источник
│   ├── dedup-log.csv         # какие кейсы были склеены как один проект
│   ├── link-check.csv        # результат проверки ссылок
│   ├── validation-report.txt # результат последней валидации
│   ├── research-report.md    # отчёт о качестве исследования
│   └── executive-summary.md  # выводы для руководителя
├── scripts/                  # валидация, merge, экспорт, проверка ссылок, отчёты
└── src/                      # приложение
```

**`data/cases.json` — единственный источник истины.** `cases.csv`, отчёты и приложение
производны от него.

## Модель данных

Каждый кейс — объект со следующими полями.

### Идентификация

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Уникальный kebab-case. Префикс страны: `ru-`, `us-`, `de-` и т.д. |
| `title` | string | Короткое название кейса — что именно внедрили |

### Кто участвовал

Интерфейс разделяет три роли и никогда их не смешивает.

| Поле | Тип | Описание |
|---|---|---|
| `client` | string | **Client** — кому внедряли. Если под NDA, описание из источника |
| `client_disclosed` | boolean | `false`, если клиент не назван |
| `client_url` | string | Сайт клиента, если известен |
| `vendor` | string[] | **Built by** — кто внедрял. Пустой массив = внутренняя команда |
| `vendor_type` | string | id из `taxonomy.vendor_types` |
| `technology_providers` | string[] | **Technology** — модель/платформа (YandexGPT, OpenAI, собственная ML) |

### Классификация

| Поле | Тип | Описание |
|---|---|---|
| `country` | string | Страна словом |
| `region` | string | id из `taxonomy.regions` |
| `industry` | string | id из `taxonomy.industries` |
| `subindustry` | string[] | id подотраслей своей отрасли |
| `business_function` | string[] | id из `taxonomy.business_functions` |
| `business_process` | string[] | 1–3 id, основной процесс первым |
| `ai_mechanisms` | string[] | 1–4 id из `taxonomy.ai_mechanisms` |

Отрасль и бизнес-процесс — **разные измерения**: один процесс встречается в разных отраслях.
На этом построен экран «Матрица».

### Содержание кейса — только факты из источника

| Поле | Тип | Описание |
|---|---|---|
| `problem` | string | Что болело у клиента |
| `before_state` | string | Как процесс был устроен до внедрения |
| `solution` | string | Что внедрили и как работает |
| `data_used` | string[] | На каких данных |
| `integrations` | string[] | С чем интегрировано |
| `deployment` | string | id из `taxonomy.deployments` |
| `stage` | string | id из `taxonomy.stages`; неизвестно — `unknown` |
| `scale` | string | Масштаб словами из источника |
| `timeline` | string | Сроки или `unknown` |
| `budget_disclosed` | number\|null | Только официально раскрытый бюджет, иначе `null` |
| `result_summary` | string | 1–3 предложения о том, что изменилось |

### Метрики

Каждая количественная величина хранится отдельным объектом:

```json
{
  "metric_type": "processing_time",
  "metric_name": "Время проверки документа",
  "baseline": "40–60 минут",
  "result": "5–10 минут",
  "delta": "6–8x faster",
  "status": "measured",
  "source_url": "https://…",
  "source_type": "vendor"
}
```

**Ни одной цифры без `source_url`, содержащего эту цифру.** Валидатор проверяет это жёстко.

`status` разделяет три принципиально разные вещи:

| Статус | Что означает |
|---|---|
| `measured` | Источник сообщает о фактически достигнутом результате |
| `reported` | Цифра заявлена стороной проекта без описания методики |
| `projected` | Ожидаемый или плановый эффект — не достигнутый |

«Ожидаемый экономический эффект — 30 млн ₽» это `projected`. Писать «AI сэкономил 30 млн»
в таком случае нельзя.

### Доказательность

| Поле | Тип | Описание |
|---|---|---|
| `sources` | object[] | `{url, title, type, publisher, date}` |
| `primary_source` | string | Один из `sources` — первичный источник |
| `evidence_grade` | `A`\|`B`\|`C` | См. ниже. `D` в базу не попадает |
| `vendor_claim` | boolean | Цифры опубликованы только подрядчиком |

### Sales Lens — интерпретация исследователя

| Поле | Тип | Описание |
|---|---|---|
| `sales_relevance` | 1–5 | Насколько кейс полезен как sales-бенчмарк |
| `why_it_matters` | string | Почему кейс важен |
| `entry_hypothesis` | string | С чем идти в похожую компанию |
| `likely_buyer` | string[] | id из `taxonomy.likely_buyers` |
| `land_opportunity` | string | Первый небольшой проект |
| `expand_opportunities` | string[] | Соседние процессы на следующий этап |
| `tags` | string[] | Свободные теги для поиска |
| `research_notes` | string | Служебное: что не удалось подтвердить |

В интерфейсе этот блок визуально отделён и подписан как интерпретация, а не как факт.

## Таксономия

`data/taxonomy.json` — **единственный** источник допустимых значений классификаторов.
Все id, встречающиеся в `cases.json`, обязаны присутствовать в нём; `npm run validate-data`
падает на любом чужом значении. Это защита от того, чтобы каждый исследователь придумывал
свои категории.

Справочники: `industries` (с вложенными `subindustries`), `business_functions`,
`business_processes`, `ai_mechanisms`, `metric_types` и `metric_groups`, `metric_status`,
`source_types`, `evidence_grades`, `stages`, `deployments`, `vendor_types`, `regions`,
`likely_buyers`, `collections`.

Расширять таксономию можно, но централизованно: добавить term в `taxonomy.json`,
поднять `version`, затем использовать в кейсах. Избегайте десятков почти одинаковых
категорий — это разрушает матрицу и фильтры.

## Методология исследования

Регламент для исполнителей: `research/RESEARCH-BRIEF.md`.

### Что считается кейсом

Компания X столкнулась с проблемой Y, внедрила решение Z, система реально работала
в пилоте или в промышленной эксплуатации, получен результат R.

Не кейс: рассуждения о возможностях AI, описание продукта без клиента, анонс намерения,
обзор рынка, научная статья без внедрения.

### Пять проходов

1. **Candidate Discovery** — широкий сбор кандидатов, русские и английские запросы,
   отдельно поиск PDF (презентации, годовые отчёты, конференционные материалы).
2. **Enrichment** — по перспективным кандидатам открыть источник и вытащить проблему,
   решение, технологию, масштаб, результат, стадию, сроки.
3. **Verification** — найти первичный источник и по возможности независимое подтверждение;
   для vendor-кейсов отдельно искать подтверждение со стороны клиента.
4. **Deduplication** — один проект часто публикуют подрядчик, клиент, облако и СМИ.
   Это один кейс: источники объединяются.
5. **Final Selection** — из сотен кандидатов отбираются лучшие подтверждённые.

Исследование велось параллельными агентами по направлениям (healthcare, construction,
energy, mining, manufacturing, retail, finance, logistics, telecom, agri, cross-industry
document AI, public/education/services) на **единой схеме данных**.

## Evidence grades

| Grade | Критерии |
|---|---|
| **A** | Назван клиент, конкретное решение, реальное внедрение, измеримый результат, первичный источник и, как правило, независимое подтверждение |
| **B** | Назван клиент, конкретное внедрение, результат понятен, но цифр мало либо информация в основном со стороны подрядчика |
| **C** | Клиент под NDA, мало деталей, нет измеримых результатов или единственный vendor-источник. Дополнительный бенчмарк |
| **D** | Описание возможности, generic use case, продуктовая страница без клиента. **В библиотеку не включается** — только `research/rejected.csv` |

Грейд виден на карточке до её открытия: пользователь должен понимать качество кейса заранее.
Если цифра опубликована только подрядчиком, кейс дополнительно помечается `vendor_claim`.

## Sales relevance и Sales Lens

`sales_relevance` от 1 до 5:

| | |
|---|---|
| **5** | Понятная боль, крупный клиент, измеримый результат, масштаб; ценность объясняется за 30 секунд |
| **4** | Хороший бенчмарк |
| **3** | Интересный, но доказательная база слабее |
| **2** | Скорее research value |
| **1** | Мало полезен для продаж |

`entry_hypothesis` — главное отличие библиотеки от обычной базы кейсов. Это гипотеза,
которую надо **проверить** у клиента, а не то, что надо ему продать.

Правильно:

> У крупных девелоперов значительный объём инженерного времени может уходить на ручную
> проверку актов КС-2 и сопоставление их со сметами и договорами. Проверить объём и
> стоимость этой работы.

Неправильно:

> Продать им Document AI.

## Правила честности данных

Они встроены и в регламент исследования, и в валидатор.

- Никогда не придумывать клиента, цифры, бюджет, сроки, технологию, масштаб.
- Ни одной количественной величины без ссылки на источник, где она опубликована.
- Не приписывать клиенту заявления подрядчика без пометки `vendor_claim`.
- Не превращать маркетинговое обещание продукта в результат клиента.
- Не выдавать PoC за production. Стадия неизвестна — `unknown`.
- Не объединять два разных проекта одной компании в один кейс.
- Не делать вывод о ROI без данных.
- Рыночную оценку не выдавать за бюджет проекта: не раскрыт — `budget_disclosed: null`.
- Факт неизвестен — `unknown` или пустое поле, а не правдоподобная догадка.

**Source Fact и Researcher Interpretation разделены структурно.** Поля описания кейса
и метрики — только из источника. Sales Lens — интерпретация, и интерфейс подписывает
её как интерпретацию.

## Интерфейс

**Пять режимов.**

- **Обзор** — счётчики и распределения по отраслям, процессам, механикам и грейдам.
  Клик по строке графика добавляет фильтр.
- **Карточки** — клиент, отрасль, процесс, проблема, решение, ключевая метрика,
  AI-механики, evidence grade, страна.
- **Таблица** — плотный режим для research, сортировка по любой колонке.
- **Матрица** — отрасль × бизнес-процесс, в ячейке число кейсов, клик открывает выборку.
  Главный способ «перещёлкивать» библиотеку.
- **Сравнение** — до 4 кейсов рядом по отрасли, процессу, масштабу, технологии,
  результатам, подрядчику, доказательности и стадии.

**Фильтры:** география и страна, отрасль и подотрасль, бизнес-процесс и функция,
AI-механика, тип результата, evidence grade, стадия, развёртывание, подрядчик,
порог sales relevance, «только с измеримым результатом», «только с измеренным (measured)
результатом», «только с названным клиентом».
Рядом с каждым значением — счётчик кейсов.

**Поиск** — полнотекстовый по компании, подрядчику, проблеме, решению, отрасли, процессу,
тегам и метрикам; русский и английский, «ё» приравнена к «е».

**Коллекции** — сохранённые пресеты фильтров: Best Sales Cases, Russian AI Cases,
Global Benchmarks, Healthcare, Construction, Energy & Mining, Retail, Finance,
Document AI, Contact Center AI, Knowledge / RAG, Predictive Maintenance, Computer Vision.

**URL-состояние.** Все фильтры пишутся в строку запроса:

```
?industry=healthcare&business_process=document-processing&region=russia-cis
```

Ссылку на подборку можно отправить команде или клиенту. Кнопка «Ссылка» копирует текущий адрес.

**Экспорт** выбранной выборки в CSV и JSON — для исследований, презентаций и подачи в LLM.

Дизайн — исследовательская база, а не лендинг: спокойная нейтральная палитра, высокая
информационная плотность, светлая и тёмная темы по настройке системы. Desktop — основной
сценарий, но интерфейс работает на планшете и телефоне: фильтры уезжают в выдвижную панель,
матрица превращается в список отраслей с процессами.

## Валидация

### `npm run validate-data`

**Ошибки** (сборка данных считается непройденной):

- пустые обязательные поля;
- неуникальный или неправильно оформленный `id`;
- значение вне таксономии, подотрасль не из своей отрасли;
- `evidence_grade: "D"` в основной базе;
- `sales_relevance` вне диапазона 1–5;
- кейс без источников; `primary_source` не входит в `sources`;
- **метрика без рабочего `source_url`**;
- неверный `metric_type` или `status`.

**Предупреждения** (работа не блокируется, но требует внимания):

- `quantitative metric without source` — в прозе есть число, а `metrics` пуст;
- Grade A без измеримого результата или с единственным источником;
- сильный sales-кейс без `entry_hypothesis`;
- вероятные дубли по `client + solution`, `client + vendor`, похожести заголовков
  и пересечению источников;
- перекос: один подрядчик даёт больше 20 кейсов, один процесс — больше 35% базы;
- недобор по квотам приёмки.

Отчёт сохраняется в `research/validation-report.txt`.

### `npm run check-links`

Проверяет каждый уникальный URL: `working`, `redirect`, `unavailable`, `broken`.
Результат — `research/link-check.csv`.

**Кейс никогда не удаляется автоматически.** Сайт может быть временно недоступен, закрыт
для дата-центров или требовать браузерных заголовков; `unavailable` — повод проверить руками,
а не удалять.

## Как добавить новый кейс

1. Найдите источник и убедитесь, что это внедрение, а не описание возможностей.
2. Найдите первичный источник и, по возможности, независимое подтверждение.
3. Проверьте, нет ли такого кейса в базе: поиск по клиенту, затем по решению.
   Если это тот же проект из другого источника — добавьте источник в существующий кейс.
4. Скопируйте шаблон из раздела 7 файла `research/RESEARCH-BRIEF.md`.
5. Заполните поля. Классификаторы берите **только** из `data/taxonomy.json`.
6. Каждую цифру положите в `metrics` с `source_url`, где она опубликована,
   и корректным `status` (`measured` / `reported` / `projected`).
7. Поставьте честный `evidence_grade` и `vendor_claim`.
8. Заполните Sales Lens: `why_it_matters`, `entry_hypothesis`, `likely_buyer`,
   `land_opportunity`, `expand_opportunities`.
9. Добавьте объект в `data/cases.json`.
10. Прогоните:

```bash
npm run validate-data
npm run check-links
npm run pipeline        # csv + отчёт + executive summary
npm run build
```

Если валидатор ругается на таксономию — **не выдумывайте новый id**, а добавьте term
в `taxonomy.json` осознанно либо выберите ближайший существующий.

## Обновление библиотеки

Для крупного пополнения (новое направление, новая отрасль) используется пайплайн исследования:

1. Дайте исполнителю `research/RESEARCH-BRIEF.md` и `data/taxonomy.json`.
2. Он кладёт результат в `research/raw/<направление>-cases.json` плюс три CSV:
   `-candidates.csv`, `-rejected.csv`, `-source-log.csv`.
3. `npm run merge-research` собирает всё в `data/cases.json`: отбрасывает Grade D,
   схлопывает дубли (объединяя источники и метрики, повышая грейд до лучшего),
   пишет сводные журналы и `research/dedup-log.csv`.
4. `npm run pipeline` — валидация, CSV, research report и executive summary.
   Отдельно `npm run check-links`: сеть медленнее остальных шагов.
5. Просмотрите глазами минимум 30 случайных кейсов: источник существует, клиент настоящий,
   summary соответствует источнику, цифры не искажены, отрасль и процесс верные, не дубль.
6. `npm run build && npm run deploy-pages`.

Порядок принципиально такой: **сначала данные, потом интерфейс.** Не расширяйте UI,
пока не подтверждена модель данных.

## Deployment

Сборка полностью статическая, `base` задан как `./` — работает из любой подпапки.

**GitHub Pages.** Соберите и положите содержимое `dist/` в публикуемый каталог
(в этом репозитории — `cases/` в корне, доступный по `/<repo>/cases/`).
Файл `.nojekyll` в корне уже есть — он нужен, чтобы Pages отдавал файлы из `assets/`.

**Cloudflare Pages / Netlify / Vercel.** Build command `npm run build`,
output directory `dist`, framework preset — Vite.

**Любой статический хостинг.** Скопируйте `dist/` куда угодно: бэкенд не нужен,
данные вшиты в бандл при сборке, внешних запросов приложение не делает.

После изменения `data/cases.json` требуется пересборка: данные импортируются на этапе сборки.
